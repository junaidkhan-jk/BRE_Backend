How to read “partial”

Partial is the row that misleads if skimmed, so every one of them names what is missing. A task is partial when part of it works and the rest was deliberately deferred — not when it is nearly done. M1-05 is the clearest example: the fuel meter and the closed function registry are finished, but evaluation walks the syntax tree rather than the compiled closure tree the design calls for. Right answers, not the designed speed.

What still has not been demonstrated

Different from work that is simply not done — this is written and reviewed, but nothing has shown it working. The list used to have four entries; three have since been demonstrated, and each of them was wrong in some way when it finally ran.

  • CI has never run. The only entry left. The workflows are valid YAML and SHA-pinned, but there is no git remote, so no pipeline has executed them. Worth distrusting: an earlier version of this page called them “lint-clean” when in fact both files were invalid YAML and could never have started — a run: line containing ": " in a plain scalar.
  • No deployment of any kind. No Dockerfile, no chart, no image, no environment. Everything that exists runs from a build directory or devstack/up.sh.
  • Nothing is authenticated. X-Tenant-Id is an unverified header (M3-09), so the decision service must not be exposed to a network you do not control. This is a deliberate ordering choice, not an oversight — but it is the kind of choice that gets forgotten, so it is written here.

Demonstrated since, and what each one cost. The decision-log SQL now runs against a real PostgreSQL — which found a tenant-owned table with no row-level security and a wrong tenant-id pattern. The engine is benchmarked — which found that half of a 100-rule decision was re-parsing expressions it had already parsed. The front end has been opened in a browser by Playwright — which found that the production page was blank, and then that 67 colour-contrast violations had been invisible because it was blank. Not one of the three was fine when it was finally checked.

Three green signals have turned out to be hiding nothing-happened. A Jupiter @Tag on a jqwik property made the platform filter skip it while the build stayed green; a grep in a pipeline swallowed a failing build's exit status; and an accessibility audit passed because the page it audited was empty. All three were caught by reading the test XML rather than the summary line.

What does work

All 90 conformance vectors from LLD §13 pass, across all twenty families. 542 tests, none failing and none skipped — the skip count is asserted, because a skipped test is not a passing test and this project has been fooled by one. That covers BEL, three-valued logic, exact decimals and dates, decision tables with every hit policy, scorecards with adverse reasons, per-entity iteration, the four aggregation modes, deviation coverage with authority resolution, knockout, fuel, and champion/challenger bucketing.

The decision service runs: POST /v1/decisions returns a decision and GET /v1/decisions/{id} reads it back, behind a decision-log port with a durable PostgreSQL mode and an in-memory mode for local work. The policy is resolved, never supplied — the caller names a policy code and may pin a bundle hash, and what gets evaluated is a signed, content-addressed bundle this pod fetched and verified.

And a real credit policy decides with it. ./devstack/up.sh builds, signs, starts and then posts the MFI reference policy's three fixtures, printing APPROVE, DECLINE and REFER — the same three answers the CI acceptance test asserts against the engine directly. That is the end-to-end claim: a lender's policy, in PSF, signed into a bundle with its parameters resolved, served through a verified pointer manifest, deciding over documents that conform to the published fact schema.

What is worth doing next

Everything below is possible without a Kafka cluster, Kubernetes, an identity provider, a penetration test or a pilot lender — which is what the whole of M3 and M4, and most of what remains in M5 and M6, does need.

  • M2-03, the registry's HTTP surface. The largest remaining gap, and the one most other things are waiting behind. Bundles, the manifest and now the resolved assets are all produced by a CLI and read from local files. Compile, sign, deploy, the §8.2 long-poll and parameter-set storage are what turn that into something an organisation can operate — and until parameter sets are stored rather than kept in a JSON file next to the policy, a lender's credit thresholds live in whatever a developer happened to commit.
  • The reason catalogue. A decision currently returns its internal reason codes and an empty list of customer-facing ones. That is the gap between a decision a credit officer can act on and one a lender can send to an applicant, and it is small: the catalogue is referenced by every policy already, and nothing reads it.
  • M2-08, the load test. The engine is benchmarked and the service is not. A 0.198 ms p99 inside the engine says nothing about what the decision-log write, the connection pool and virtual-thread scheduling do to it under 500 decisions a second.
  • M2-06, facts encryption behind KmsPort. Fact snapshots are not stored at all today, which is the safe default and also means replay cannot be used for the thing it exists for. The §9.2 two-envelope scheme is what unblocks it.
