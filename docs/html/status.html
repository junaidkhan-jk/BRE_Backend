How to read “partial”

Partial is the row that misleads if skimmed, so every one of them names what is missing. A task is partial when part of it works and the rest was deliberately deferred — not when it is nearly done. M1-05 is the clearest example: the fuel meter and the closed function registry are finished, but evaluation walks the syntax tree rather than the compiled closure tree the design calls for. Right answers, not the designed speed.

Four things that exist but are unproven

Different from work that is simply not done — these are written and reviewed, but nothing has demonstrated them working.

  • The decision-log SQL has never been executed. The migrations are written against LLD §5.3 and read through, but no database has run them. Embedded PostgreSQL works on this machine — verified, about four minutes — if you want them proven.
  • CI has never run. The workflows are written and lint-clean, but there is no git remote, so no pipeline has ever executed them.
  • The engine has not been benchmarked. All 90 conformance vectors pass, and the fail-closed property now runs against the real engine at 10⁶ cases. Fuzzing has been done and found a real parser crash, since fixed, with roughly 18 million executions clean after it — though no single campaign ran its full 30-minute budget to a clean exit in one go. The JMH latency budgets (M1-16) have not been run at all, so no performance figure for this engine exists.
  • The front end was not opened in a browser. The blank-page fix is verified by mechanism (classic script tag, IIFE bundle, nothing fetched at load) but not by sight: the Playwright server failed to connect.
  • Two green signals turned out to be hiding nothing-happened. A Jupiter @Tag on a jqwik property made the platform filter skip it while the build stayed green, and a grep in a pipeline swallowed a failing build's exit status. Both were caught by reading the test XML rather than the summary line, and both are worth distrusting a BUILD SUCCESSFUL for.

What does work

All 90 conformance vectors from LLD §13 pass, across all twenty families — 363 tests, none failing. That covers BEL, three-valued logic, exact decimals and dates, decision tables with every hit policy, scorecards with adverse reasons, per-entity iteration, the four aggregation modes, deviation coverage with authority resolution, knockout, fuel, and champion/challenger bucketing.

The decision service runs: POST /v1/decisions returns a decision and GET /v1/decisions/{id} reads it back, behind a decision-log port with a durable PostgreSQL mode and an in-memory mode for local work.

What is worth doing next

All three are possible without a Kafka cluster, Kubernetes, a penetration test or a pilot lender — which everything in M3, M4 and M6 does need.

  • M1-10, static checks. Reject a policy with a decision-table gap at authoring time rather than mid-decision. A policy that fails mid-decision has already cost a decision.
  • M1-13, bundle signing. Without a signed, content-addressed bundle there is no registry — which is why the policy still arrives inline on every request, the largest deviation in the API today.
  • M1-14, the fact model. Unblocks M2-05 replay, and is the first step toward the §9.2 encryption that would let facts be stored at all.
