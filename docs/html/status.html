How to read “partial”

M3-02studio-service — version lifecycle, PSF import/export, diff
The lifecycle is built, in policy-registry rather than a separate service — one control-plane deployable while there is one database and one set of §5.2 tables; splitting it would give two services the same schema and no boundary between them. DRAFT → IN_REVIEW → APPROVED → ARCHIVED with both side transitions, optimistic locking so two authors in one draft is an error rather than a silent lost edit, and the author's PSF source kept verbatim beside the IR (V9) because translation discards every comment — and a credit policy's comments are where the reason for a threshold lives. The diff is built, and it is two diffs — a semantic one over the compiled policy keyed by component code, so reordering rules or reflowing a block shows as no change at all, and a text one over the source, because the comment explaining a threshold is sometimes the most review-worthy part of a change. A reviewer asked to approve a 400-line text diff that changes nothing approves the next one without reading it. Import is built too: PSF carries no tenant and no bundle hash, which is exactly what makes a policy portable — the receiving installation compiles it against its own parameter sets, so the same document means different thresholds for different lenders. An import lands as a DRAFT and is marked imported, because one arriving APPROVED would be a way to put a policy live with nobody at the receiving lender having read it; source that does not translate creates no policy row at all, since a code reserved for a document nobody can compile collides with the next import of the same policy. Export is the version's source, byte for byte. Signed bundle interchange is separate and is M3-07.

M3-04Test cases, coverage, submit gates, simulation API
Test cases are stored per version and re-run on every save, against the tenant's resolved parameters — the same ones the bundle will be signed with, because a test run against different thresholds from the deployed ones is not a test of anything. POST …/versions/{n}/run evaluates any version — including a DRAFT — against supplied facts, returning per-step and per-entity outcomes with the measure a deviation was judged on.

Coverage is measured by the engine, not estimated. A probe on the evaluation context records which rule statuses were reached, which decision-table rows fired and which scorecard bins scored; the denominators come from the policy itself. Two distinctions carry the whole value: a row that matched and lost to a FIRST hit policy is not covered, because nothing it says has ever affected an outcome; and a rule's denominator is only the statuses it can actually reach, so a rule with no guard is never charged for NOT_APPLICABLE. The missing-data branch is counted — “what happens when the bureau is down” is the least-tested and most-consequential path in a credit policy, and a happy-path-only suite must not score 100%.

The submit gate now refuses five things (FR-LIFE-002): a static-check error, a failing case, no cases at all, coverage below the tenant's threshold (default 80%, a tenant setting, every change audited with its before and after), and a missing change note or committee reference. The refusal names the uncovered items rather than counting them — AC-TEST-003 asks for an untested row by name, and a count tells an author they have a problem while a name tells them where it is. Measured against the reference policy, the three acceptance fixtures cover 28.6%; that figure is now asserted in CI with a floor and a ceiling, and recorded as a finding against M6-01's 90% exit criterion.

On the decision path the probe is a no-op constant, so a production decision pays nothing for a measurement nobody asked for.

M3-05Segregation of duties
Enforced twice — in the application and by database triggers, which is §5.2's own design and the reason it matters: a trigger holds for every writer, including psql. The reviewer cannot be any editor, not merely the creator, because a draft handed between two people must not become reviewable by either. A deployment approver can be neither author, reviewer nor requester. The administrator override is a tenant column, needs a granted role, and writes SOD_OVERRIDDEN to the hash-chained audit log on every use; V12 states plainly what it costs. Asset reviews and the four-eyes rules on shared assets are not built (M3-03).

M3-06Deployments, approvals, scheduling, rollback, manifests
PENDING_APPROVAL → ACTIVE → SUPERSEDED, with ROLLED_BACK and CANCELLED; per-environment approval counts (DEV 0, UAT 1, PROD 2); and activation that publishes a signed manifest in the same transaction — a deployment row no pod can see is a statement of intent, not a deployment. A rollback is a new deployment pointing at a previous bundle: nothing is edited in place, which is the difference between being able to answer “what was serving at 14:30 last Tuesday” and not.

Scheduling is built, and 00 §3.4's SCHEDULED state is now reachable. It was in the status CHECK and nothing ever set it: approving the last required approval activated immediately and ignored effective_from — which could not even be requested, because the field was hardcoded to now(). A lender scheduling a rate change for the start of the next business day got it live during the current one, and every application decided in between was decided under the wrong policy. A future-dated deployment now waits in SCHEDULED and a timer promotes it, claiming each row with FOR UPDATE SKIP LOCKED — two registry instances polling the same table is the normal case, and without the claim both would publish a manifest and audit an activation. The comparison is against the database's clock, so two pods with drifting clocks cannot disagree about whether a change is due, and a timed activation is a distinct audit action from a human one.

Found by writing the test: a @Transactional method called from another method of the same bean is not proxied, so the tenant scope died with its own statement and row-level security filtered every due deployment while the database plainly held one. And BYPASSRLS is not a table privilege — the lookup role could see past every policy and still not read deployments.

M3-10Studio audit events
Every lifecycle act writes to the hash-chained, append-only audit_log: created, saved, submitted, reviewed, approved, deployed, rolled back, logins and refusals, role grants, SoD overrides. The chaining is a database trigger, not application code — it assigns the sequence under a row lock, stamps the time from the server, and two further triggers forbid UPDATE, DELETE and TRUNCATE. The lifecycle test verifies the chain has no gaps and no broken links, by reading what the trigger built.

The read API is built, and there is deliberately no write path — an HTTP route that could append an entry would let a caller author history. It filters by action prefix, subject, actor and time, and /verify recomputes every hash from its predecessor using the trigger's own expression rather than reading a stored flag, because a flag is exactly what somebody tampering would set. It reports the first broken link and the first sequence gap by position, and returns the head hash in full — the value to record outside this database if the chain is ever to be shown untampered to somebody who does not trust it. AUDIT_READ is its own grant, so an author with POLICY_READ cannot read the record of their colleagues' actions. Not built: the §10.4 signed export.

What still has not been demonstrated

Different from work that is simply not done — this is written and reviewed, but nothing has shown it working. The list used to have four entries; three have since been demonstrated, and each of them was wrong in some way when it finally ran.

  • CI has never run. The only entry left. The workflows are valid YAML and SHA-pinned, but there is no git remote, so no pipeline has executed them. Worth distrusting: an earlier version of this page called them “lint-clean” when in fact both files were invalid YAML and could never have started — a run: line containing ": " in a plain scalar.
  • No deployment of any kind. No Dockerfile, no chart, no image, no environment. Everything that exists runs from a build directory or devstack/up.sh.
  • Nothing is authenticated. X-Tenant-Id is an unverified header (M3-09), so the decision service must not be exposed to a network you do not control. This is a deliberate ordering choice, not an oversight — but it is the kind of choice that gets forgotten, so it is written here.

Demonstrated since, and what each one cost. The decision-log SQL now runs against a real PostgreSQL — which found a tenant-owned table with no row-level security and a wrong tenant-id pattern. The engine is benchmarked — which found that half of a 100-rule decision was re-parsing expressions it had already parsed. The front end has been opened in a browser by Playwright — which found that the production page was blank, and then that 67 colour-contrast violations had been invisible because it was blank. Not one of the three was fine when it was finally checked.

Three green signals have turned out to be hiding nothing-happened. A Jupiter @Tag on a jqwik property made the platform filter skip it while the build stayed green; a grep in a pipeline swallowed a failing build's exit status; and an accessibility audit passed because the page it audited was empty. All three were caught by reading the test XML rather than the summary line.

What does work

All 90 conformance vectors from LLD §13 pass, across all twenty families. 542 tests, none failing and none skipped — the skip count is asserted, because a skipped test is not a passing test and this project has been fooled by one. That covers BEL, three-valued logic, exact decimals and dates, decision tables with every hit policy, scorecards with adverse reasons, per-entity iteration, the four aggregation modes, deviation coverage with authority resolution, knockout, fuel, and champion/challenger bucketing.

The decision service runs: POST /v1/decisions returns a decision and GET /v1/decisions/{id} reads it back, behind a decision-log port with a durable PostgreSQL mode and an in-memory mode for local work. The policy is resolved, never supplied — the caller names a policy code and may pin a bundle hash, and what gets evaluated is a signed, content-addressed bundle this pod fetched and verified.

And a real credit policy decides with it. ./devstack/up.sh builds, signs, starts and then posts the MFI reference policy's three fixtures, printing APPROVE, DECLINE and REFER — the same three answers the CI acceptance test asserts against the engine directly. That is the end-to-end claim: a lender's policy, in PSF, signed into a bundle with its parameters resolved, served through a verified pointer manifest, deciding over documents that conform to the published fact schema.

What is worth doing next

Everything below is possible without a Kafka cluster, Kubernetes, an identity provider, a penetration test or a pilot lender — which is what the whole of M3 and M4, and most of what remains in M5 and M6, does need.

  • M2-03, the registry's HTTP surface. The largest remaining gap, and the one most other things are waiting behind. Bundles, the manifest and now the resolved assets are all produced by a CLI and read from local files. Compile, sign, deploy, the §8.2 long-poll and parameter-set storage are what turn that into something an organisation can operate — and until parameter sets are stored rather than kept in a JSON file next to the policy, a lender's credit thresholds live in whatever a developer happened to commit.
  • The reason catalogue. A decision currently returns its internal reason codes and an empty list of customer-facing ones. That is the gap between a decision a credit officer can act on and one a lender can send to an applicant, and it is small: the catalogue is referenced by every policy already, and nothing reads it.
  • The durable write under load. The service holds 500 decisions a second at a 14 ms p99 — but with the IN_MEMORY decision log. NFR-PERF-01's budget includes the durable write, and the one thing M2-08 does not yet measure is the PostgreSQL path with its sixteen- connection pool.
