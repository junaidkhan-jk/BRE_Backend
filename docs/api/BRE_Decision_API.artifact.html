BRE Decision API

The integration reference for the BRE Platform's synchronous Decision API, for engineers connecting a Loan Origination System to it. Generated from the OpenAPI 3.1 contract in bre-contracts and the implemented service, and it describes what is built today — the differences from the full specification are listed in Part 3 rather than glossed over. 8 October 2026.

On this page
PART 1 — ORIENTATION

What is this API?

What this means: You send an application's facts and the policy to judge them by; it sends back a decision — approve, refer, decline — and the reason for every rule it ran.

The BRE Decision API is the synchronous front door of the decision engine. One call in, one decision out, in tens of milliseconds. It is the call a Loan Origination System makes when a credit officer presses Submit.

Why does it look like this?

What this means: The engine is a pure calculation — it never phones a bureau or a KYC service — and almost every other rule in this document follows from that one choice.

Decision D2 fixes the Decision API as a pure function of (facts, policy, asOf). The caller assembles a complete fact snapshot; the engine decides. Three consequences matter to you as an integrator:

Because the engine fetches nothing…You get
the same inputs always give the same outputExact replay. A decision from last March can be reproduced byte for byte, which is what makes GET an audit record rather than a log line.
there is no outbound call on the hot pathPredictable latency. Evaluation time is a property of your policy and your data — never of someone else's uptime.
bureau reports and KYC documents are never cached hereA smaller regulated surface. The engine holds no data it did not receive on the request.
PART 2 — USING IT

How do I get a decision?

What this means: POST the facts and the rules to one endpoint; you get the decision back in the same response.

POST /v1/decisions — live

POST /v1/decisions
Content-Type: application/json

{
  "tenantId":  "t_acme",
  "requestId": "REQ-2026-0001",
  "asOf":      "2026-10-01",
  "facts": {
    "application": { "applicationRef": "APP-2026-000123" },
    "member":      { "income": "20000", "emi": "5000", "age": 34 }
  },
  "policy": {
    "rules": [
      { "code": "MFI_FOIR_CAP",
        "check": "member.emi / member.income <= 0.5",
        "reasonCode": "POL_FOIR_EXCEEDED" }
    ]
  }
}

The four fields that decide everything

FieldRequiredWhat it does, and what goes wrong
tenantIdyesThe platform is multi-tenant from day one (D1). The tenant appears on every row, event, metric and log line, so it is never defaulted.
requestIdyesYour idempotency key. Retrying with the same (tenantId, requestId) returns the original decision with the same decisionId — not a second decision.
asOfoptionalThe date the policy is evaluated against. Omit it and the service resolves one once, from the tenant time zone, and stores it. The engine itself never reads a clock — it only ever sees this date, which is what makes replay exact.
factsyesThe snapshot. Two rules below are where integrations actually go wrong.

Two rules about facts worth reading twice

Send decimals as JSON strings. "20000", not 20000.00. A decimal that passes through a JSON number may be read as a double somewhere in the chain, and a double is exactly how 0.1 + 0.2 stops equalling 0.3. The engine uses exact decimal arithmetic throughout; sending a float undoes that before the value arrives.

An absent field is missing data, which is not zero. Leave a field out and a policy that needs it reports DATA_MISSING and the decision refers to a human. Send 0 for an income you do not know and you have asserted that the borrower earns nothing — a different and much worse claim, and one the engine will act on.

What comes back?

What this means: One overall decision, plus the status of every rule that ran — so you can always show why.

{
  "decisionId":  "01a11b0b-df03-76a2-a30c-255a7934d513",
  "tenantId":    "t_acme",
  "requestId":   "REQ-2026-0001",
  "asOf":        "2026-10-01",
  "decision":    "APPROVE",
  "stpEligible": true,
  "results": [
    { "code": "MFI_FOIR_CAP", "status": "PASS" }
  ]
}

The decisionId is a UUIDv7, so it carries its own creation time. The decision store derives the row's partition from it — which is why reading one decision reads one day's partition instead of scanning every day the store holds.

How the overall decision is reached

Rule statuses

StatusMeans
PASSThe check was TRUE.
FAILThe check was FALSE.
DEVIATIONFailed within a tolerance an authority may approve.
DATA_MISSINGA fact the rule needed was absent.
REFERThe rule asks for human review.
NOT_APPLICABLEThe rule's when guard was FALSE.
ERRORThe rule could not be evaluated. See the error field.

stpEligible deserves its own note: it is false the moment anything deviates, including a deviation an approver has already signed off. The decision is then APPROVE, but it was never straight-through, and the two facts are worth keeping apart in your own reporting.

How do I read a decision back?

What this means: Fetch any past decision by its ID — this is the audit record.

GET /v1/decisions/{decisionId} — live, with header X-Tenant-Id.

The lookup is tenant-scoped. A correct decisionId under the wrong tenant returns 404, not 403 — a decision is never readable across tenants (D1), and 404 is also the answer that leaks least, since a 403 would confirm the ID exists.

Why the tenant is a header today, and why that is temporary

The specification derives the tenant from the authenticated principal, which is the only trustworthy source. A header is accepted now because there is no authentication yet. In this form a caller can read another tenant's decision by changing one header, so this endpoint must not be exposed to an untrusted network until the OAuth2 resource server lands.

What happens when data is missing?

What this means: Missing data never produces an approval — it refers the application to a person.

This is decision D9, and it is the single most important property of the engine. A fail-open engine approves loans because data was absent, which is a credit loss and a regulatory finding at once. Draft 1 of this product had that defect; the current engine closes it, and a property-based test asserts it over randomly generated policies.

Concretely: if you see a REFER you did not expect, the cause is almost always a fact the policy needed and your request did not carry. Check the results array for a rule with DATA_MISSING — its reasonCode names the symbol.

What can go wrong?

What this means: Bad requests get an HTTP error; rules that break mid-evaluation are reported inside a normal 201 response.

StatusWhenBody
201Decided. Including when a rule errored — the engine still produced a decision.The decision
400The request body is not valid.application/problem+json
422A BEL expression does not parse. The body carries line and column.application/problem+json
404No such decision for that tenant.empty

Error bodies follow RFC 9457 and name the offending field, never its value. A validation message that quoted your submitted facts would put personal data into client logs and error trackers, where the engine no longer controls who reads it.

Runtime error codes

These arrive on a rule result, not as an HTTP status, because the decision still exists — it is REFER.

CodeCause
EVAL_DIV_ZERODivision by zero. The one integrators hit most. Division by zero is an error, not a missing value — guard it: income > 0 and emi / income <= 0.5. and short-circuits, so the division never runs when the guard is false.
EVAL_OVERFLOWInteger overflow.
EVAL_FUEL_EXHAUSTEDThe policy exceeded its evaluation budget. Every component not yet evaluated is also reported ERROR — never "not applicable", which would read as a decision nobody made.
EVAL_TABLE_NO_MATCHEvery decision-table input was present and no row matched — a gap in the policy.
EVAL_TABLE_UNIQUE_VIOLATIONMore than one row matched under a UNIQUE hit policy.
EVAL_SCORECARD_NO_BINA characteristic had a value but no bin covered it.
EVAL_PARAM_NOT_EFFECTIVEA referenced parameter has no value effective at asOf.
EVAL_INTERNALAn engine defect. Raises a P1 alert.
PART 3 — LIMITS AND HONESTY

What is not built yet?

What this means: This API is a working subset of the specified one — here is exactly what is missing, so you do not design against something that is not there.

ConcernTodaySpecified
Policy sourceinline on the requestResolved from a signed, content-addressed bundle by hash. A caller cannot choose the policy that decides its application.
AuthenticationnoneOAuth2 client credentials, scope decisions:evaluate.
Idempotency keyin the bodyIdempotency-Key header.
Explanation endpointnot builtGET /v1/decisions/{id}/explanation, regenerated by replaying the stored facts.
Per-entity resultsone result per rulePer-entity results, deviations with required approval level, customer-facing reasons.
Facts at restnot stored by defaultEnvelope-encrypted and split by identifying field group, so erasure is key destruction.
TransportREST onlyREST and gRPC.

The inline policy is the biggest of these. It is a development affordance that makes the API testable before the policy registry exists. It is not how a deployment works, and any integration built around sending your own rules will have to change.

Why facts are not persisted, and what that costs you

Replay needs the facts. The specification requires them stored as two envelopes under a tenant key and a per-principal key, so that erasing a borrower is performed by destroying a key rather than by hunting rows. That key hierarchy is not built.

Storing them as plaintext in the meantime was rejected. The table exists, its column is named facts_json_plaintext rather than anything that sounds encrypted, and it is written only behind an explicitly-named flag that defaults to off.

What this costs: a decision is durable, auditable and idempotent, but the full evaluation trace cannot be regenerated. You get the decision and every rule's status; you do not get a replay.

What this means: The choices behind this API's shape, and why each was made.

RefDecisionRationale
D2Facts in, decision out — the engine calls nothingDeterminism makes replay, simulation and back-testing exact, keeps latency in single-digit milliseconds, and keeps regulated data out of the engine.
D9Fail-closed: ERROR and DATA_MISSING can never produce APPROVECloses the fail-open defect in Draft 1, where absent data could approve a loan.
D8Exact decimals; evaluation never reads a clockMoney is not a double, and a replay that re-derives "today" is not a replay.
D6Durable write before the response returnsRPO 0 for an acknowledged decision.
D1Tenant on every row, and on every readTenancy costs little to build in and is very expensive to retrofit.
